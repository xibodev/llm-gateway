Identity and policy

Every key acts as someone, inside a project.

Identity, private and shared credentials, membership, policy, usage, and alerts stay attached to each request.

GovernanceIdentityAuthenticationConnectionsKeysQuotasAudit

The gateway uses trusted reverse-proxy SSO for humans and scoped gateway keys for CLIs and services. It remains a single-node control plane.

Identity model

  • Human: SSO-provisioned and able to own private provider connections.
  • Service: administrator-created workload identity that cannot own human subscriptions.
  • System: built-in owner for gateway-managed credentials.
  • Project: membership and aggregate-policy boundary.
  • Roles: owner, admin, member, and viewer.

Authentication boundaries

Admin APIs accept the static recovery key or verified admin-group SSO. Portal APIs require verified human SSO and same-origin mutation. Data-plane APIs accept static or project keys. Project keys are never administrator credentials.

Provider connections

Humans can own named encrypted connections. Generic API-key resolution is private default, system connection, then legacy config seed. Copilot services require an exact active project/provider/service binding. Codex OAuth is experimental and human-private.

Narrow binding claimThe exact binding requirement applies to the supported Copilot shared-service path. Generic system API-key fallback is not project-binding-gated today.

Gateway keys

Keys authenticate by SHA-256 hash and belong to one principal/project. If encryption was configured at issuance, an encrypted copy can be revealed by its human owner or an administrator. Older hash-only keys return 409 on reveal. Reveal responses are no-store and audited.

Policy and quotas

Project and key policy intersect across model/provider allowlists, RPM, daily/monthly requests, tokens, estimated cost, and model credits. Request counts are consumed before dispatch. Token, cost, and credit limits can exceed by one in-flight request.

These are gateway limits, not provider subscription quota scheduling.

Usage, audit, and alerts

Usage records request attribution, status, latency, requested and served model, provider, tokens, estimated cost, credits, and errors. Audit is append-only during its configured retention period; the project does not claim every management mutation is covered.

Quota and key-expiry rules create a durable outbox. An external worker performs delivery.
