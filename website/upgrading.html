Before an upgrade

  1. Schedule maintenance, drain traffic, and stop all gateway writers.
  2. Check the installed binary's llmgw --help. v0.1/v0.2 lack the backup CLI; v0.3.1 supports it. Use built-in backup only if available; otherwise snapshot the entire stopped state volume, including SQLite WAL/SHM, configuration, secrets, and caches.
  3. Record the image digest or binary checksum.
  4. Retain the original encryption key, deployment environment, state mounts and configured external config/database/cache paths.
  5. Read the release notes and test extraction into a separate location.

Keep the original snapshot unchanged outside automatic retention. Do not start the new binary on original state just to make a backup. Follow the repository-versioned recovery procedure.

Standalone image installation

Use this for the published-image quickstart, which pins ghcr.io/xibodev/llm-gateway:0.3.1. Select a future version from release notes.

  1. Complete the offline backup checklist using the installed image. Keep the original snapshot outside the volume and automatic retention.
  2. Preserve your installation folder, compose.yaml, .env, project name and state:/state volume. Keep the original administrator and encryption keys; do not generate replacements. Remove stale shell overrides.
  3. Change only image: in compose.yaml to the selected published version/digest.
  4. From that same folder, in POSIX or PowerShell:
standalone installation · after backup
docker compose pull gateway
docker compose up -d gateway

No clone, --build, override file or LLMGW_IMAGE variable is involved. Compose reads the same .env automatically. Check startup logs, running version, health, authenticated administrator state and intended provider access before restoring traffic. Keep the prior image and snapshot until acceptance.

Native binary installation

After the same offline backup, download and verify the replacement archive. Stop the old process before replacing its executable. Run llmgw serve (or .\llmgw.exe serve) with the saved keys and the same absolute state/config paths, not a maintenance user's default ~/.llmgw. Preserve the old binary and original snapshot together.

Developers: source installation

For the root source Compose recipe, back up offline, select the intended source tag in the same clone, and preserve its private .env, config.local.yaml, project and llmgw-state volume. Do not overwrite config with the example. Use LLMGW_HOST_PORT=127.0.0.1:8787, not standalone LLMGW_PORT, and clear stale shell overrides before rebuilding:

repository root · source build only
docker compose --env-file .env up -d --build

Existing production stacks must keep their actual files, overrides, environment and mounts; follow the deployment-specific procedure. Neither released repository Compose file supports LLMGW_IMAGE by itself; that procedure adds the variable to private configuration explicitly.

State migration

Applicable legacy keys, usage, credential structures, and bindings migrate idempotently. Incompatible catalog cache entries are discarded and rediscovered. Existing encrypted system connections are not overwritten by config seeding.

Restore rejects a backup schema newer than the running binary.

Rollback

Restore the original pre-upgrade snapshot into an empty replacement volume/directory, including original WAL and external state, ownership/permissions, environment and encryption key. Never overlay migrated state or run the old image against the migrated database. There is no supported database downgrade.

Run the matching prior binary or image by exact version/digest, then verify health, authenticated admin state, models and a small completion for each intended credential scope. Rollback discards writes made after the snapshot. See the recovery checklist.
