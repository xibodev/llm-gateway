Deployment profiles

Published image (recommended)

Use the standalone Compose recipe, pinned to ghcr.io/xibodev/llm-gateway:0.3.1. No clone, build or config seed is required. From your private installation folder containing compose.yaml and the generate-once .env:

POSIX or PowerShell · start / stop
docker compose up -d
docker compose down

The first command starts; the second stops without deleting state. Preserve the folder, Compose project, .env and state:/state volume. Remove stale shell overrides for both keys and the optional host-port variable LLMGW_PORT. The container stays on port 8787, runs as UID/GID 65532 and already has an exec-form /llmgw health healthcheck. Do not replace it with shell/curl commands: the image has no shell.

Never regenerate the encryption key with existing state; back it up separately. Use image upgrades, not a rebuild. Never use down -v for routine maintenance.

Native binary

Download, verify and unpack a release binary. It does not automatically read .env. Load saved keys and the same explicit state/config paths for every service and maintenance invocation. Native state is independent of Compose volumes.

Developers: source build

The source-only recipe uses the repository root docker-compose.yml. It builds the worktree, seeds /state/config.yaml from config.local.yaml once, and uses a separate llmgw-state volume. Set LLMGW_HOST_PORT=127.0.0.1:8787 in that clone's private .env; otherwise the root default publishes on all interfaces. After preparing that recipe and clearing stale shell overrides:

repository root · source build only
docker compose --env-file .env up -d --build

Keep source and standalone folders, projects and volumes separate. Console edits and restores change the volume copy, not the seed.

Existing source-based TLS deployment

The production example also uses build: and a local image name. Neither repository Compose file supports LLMGW_IMAGE by itself. To convert an existing stack to a published image, follow the private image-override instructions and complete deployment and rollback procedure. Retain its actual files, environment, project and mounts; this is not the standalone quickstart. Choose a published version/digest from release notes, not a floating tag.

Remote identityThe included Caddyfile is not turnkey SSO. For multi-user deployment, add trusted identity middleware that overwrites the SSO secret header and blocks direct gateway access.

Health and build identity

probes
curl -fsS https://<GATEWAY_HOST>/health
llmgw version

Both report semantic version, source commit, and commit-derived RFC3339 time. Health proves process liveness. Use provider Test completion for inference readiness.

Request logs

Logging is off by default. Metadata logging covers POST /v1/*. Unsafe body logging requires a second explicit flag and can persist prompts, credentials, PII, and source code. Logs retain the active file and one size-rotated generation and are excluded from backup.

Retention starts asynchronously after startup and repeats every 24 hours. SQLite deletion is batched. Pending/failed outbox work, current quotas, identities, credentials, policies, and provider state are preserved.

Create and inspect a backup

Check the installed binary's llmgw --help first. v0.1/v0.2 have no backup CLI; v0.3.1 provides these commands. Stop all writers and keep the service's actual state/config environment before using them.

No backup command?Archive the entire stopped state volume, including SQLite -wal/-shm, config, secrets, and caches. Snapshot configured external config/database/cache paths too. Retain the original encryption key and deployment environment separately. Do not start a newer binary on original state to make a backup. Follow the offline snapshot procedure.
offline maintenance · backup-capable binary
llmgw backup create
llmgw backup inspect <ARCHIVE>

No-path create writes into the retention-managed state backup directory. A supplied external path is not pruned automatically. For Compose, use the offline one-shot container procedure with the installed image, same environment, project and state mount; do not run a host binary against its default home instead. Copy the archive to protected storage outside the volume.

The archive includes runtime config, checkpointed gateway/telemetry/configured savings SQLite, catalog, recognized Copilot cache, and applicable legacy key/secret state. Environment keys and request logs are excluded. Protect archives from disclosure and replacement: checksums detect corruption, not authenticity.

Restore and recovery

offline restore
llmgw backup inspect <ARCHIVE>
llmgw backup restore <ARCHIVE> --force
llmgw serve

Restore validates first and replaces known state; it is not a merge. An interrupted prepared transaction is rolled back on the next start. A committed transaction resumes cleanup. Newer unsupported schemas are rejected.

Keep the original encryption key separately. Configure archived external savings/cache destinations in the current process before restore.

Release evidence

Stable tags on approved main commits produce five platform archives, five SPDX SBOMs, verified checksums, GitHub provenance, and a versioned Linux amd64/arm64 GHCR image with SPDX/SLSA attestations. Manual dispatch is non-publishing and retains no artifact.

For a single download, compare its SHA-256 against the exact filename in SHA256SUMS before unpacking; use Get-FileHash -Algorithm SHA256 on Windows or shasum -a 256 on macOS. The full checksum command below expects the complete artifact set.

verify
sha256sum -c SHA256SUMS
gh attestation verify llmgw_v<VERSION>_linux_amd64.tar.gz \
  --repo xibodev/llm-gateway
docker buildx imagetools inspect \
  ghcr.io/xibodev/llm-gateway:<VERSION>

Rollback

  1. Stop all writers; preserve failed upgraded state separately.
  2. Restore the original pre-upgrade snapshot into an empty replacement volume, including original WAL and external state. Never overlay migrated state.
  3. Restore original ownership, permissions, environment, mounts and encryption key. Keep the same Compose project.
  4. Start the matching previous image by version/digest.
  5. Verify health, authenticated admin state, and model listing plus one completion for each human and service/project credential scope.

There is no supported database downgrade. Never run the old image against migrated state or leave newer WAL files behind. Rollback discards writes after the snapshot. Keep the original snapshot outside automatic backup retention and never run down -v during an upgrade.
